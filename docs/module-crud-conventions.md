# 常用模块 CRUD 规范

本文只总结“后台常规配置型模块”的默认开发技法，方便你给 Codex 提需求时直接复用。

适用场景：

- `VIP` 等级配置
- 分类配置
- 品牌配置
- 标签配置
- 频道配置
- 各类字典型、配置型、枚举型后台模块

不适用场景：

- 订单、支付、库存这类强事务模块
- 登录、权限、菜单这类 system 模块
- 前台 `/api` 业务接口

## 1. 这类模块的默认目标

这类模块通常不是复杂业务，而是“后台维护基础配置数据”。

所以默认目标是：

1. 字段清晰
2. 列表稳定
3. 状态可控
4. 排序可控
5. 方便前端下拉、列表、开关使用

## 2. 配置型 CRUD 建议默认字段

如果你没有特别说明，Codex 可以优先按下面思路建字段。

### 2.1 通用建议字段

大多数配置型模块，建议至少考虑这些字段：

1. `id`
2. `name`
3. `status`
4. `sort`
5. `remark`
6. `created_at`
7. `updated_at`

推荐理解：

- `name`：名称，给后台列表和前台展示用
- `status`：状态，控制启用/禁用
- `sort`：排序，控制展示顺序
- `remark`：备注，给运营和后台说明用

### 2.2 为什么很多模块最好带 `status`

`status` 基本是配置型模块的默认字段，原因很直接：

1. 很多数据不是删掉，而是停用
2. 前台通常只展示启用数据
3. 后台需要保留历史配置，但暂时不生效

所以像这些模块，通常都建议有 `status`：

- `VIP` 等级配置
- 分类配置
- 品牌配置
- 标签配置
- 活动配置

如果你没特别说明，Codex 可以默认把 `status` 作为常规字段考虑进去。

### 2.3 为什么很多模块最好带 `sort`

`sort` 也是配置型模块的高频字段，尤其是“前台会按顺序展示”的数据。

建议带 `sort` 的典型模块：

1. 分类
2. `VIP` 等级
3. 品牌
4. 导航项
5. 标签

原因：

1. 前端经常需要稳定排序
2. 不能完全依赖 `id` 或创建时间排序
3. 运营经常会手动调顺序

### 2.4 分类配置建议一定有 `status` 和 `sort`

像分类、栏目、频道、标签分组这类模块，默认建议至少有：

1. `name`
2. `status`
3. `sort`

因为这类数据天然有两个需求：

1. 要控制是否显示
2. 要控制显示顺序

所以当你说“做一个分类配置 CRUD”，如果没特殊说明，Codex 应优先按有 `status` 和 `sort` 的结构实现。

### 2.5 `VIP` 等级配置建议字段

`VIP` 等级配置属于典型的后台配置模块，建议优先考虑这些字段：

1. `id`
2. `name`
3. `level`
4. `status`
5. `sort`
6. `remark`

如果还有权益类配置，再按需求补：

1. 折扣
2. 升级门槛
3. 图标
4. 背景图
5. 权益说明

这里的重点不是字段必须完全一致，而是：

- 一般要有 `status`
- 一般要有 `sort`
- 一般要有唯一的等级标识，例如 `level`

## 3. 列表接口什么时候该分页

这件事不要一刀切。不是所有列表都应该分页。

### 3.1 应该分页的场景

符合下面任一情况，默认建议分页：

1. 后台管理主列表
2. 数据量可能持续增长
3. 需要按关键词、状态、时间等条件筛选
4. 需要给表格展示
5. 前端页面有分页器

典型例子：

1. 用户列表
2. 用户地址列表
3. 订单列表
4. 操作日志列表
5. 登录日志列表

一句话判断：

“这类数据会持续增长，而且后台要检索”，通常就该分页。

### 3.2 不应该分页的场景

符合下面任一情况，默认建议不分页：

1. 只给下拉框使用
2. 数据量很小且长期稳定
3. 只需要全部启用项
4. 只是给前端选择器、弹窗、联动组件提供数据

典型例子：

1. 分类下拉选项
2. 启用中的 `VIP` 等级选项
3. 品牌下拉列表
4. 标签选择器
5. `VIP` 等级管理
6. 分类管理

一句话判断：

“这是选项列表，不是后台主表格”，通常就不分页。

### 3.3 按模块类型的默认判断

有些模块不能只看“是不是后台页面”，还要看数据规模和使用方式。

默认按下面理解：

1. `VIP` 等级：通常数量少，默认优先不分页
2. 分类：通常数量少，默认优先不分页
3. 品牌：可能少，也可能多，默认要先提醒你确认是否分页
4. 用户：默认分页
5. 用户相关列表：默认分页

其中品牌最容易出现两种情况：

1. 如果只是少量品牌配置，可以只做 `/list`
2. 如果品牌数量明显会增长，或者后台有表格筛选需求，就做 `/pageList`

### 3.4 一般一个模块会同时有两种列表

一个配置型模块，通常建议同时存在：

1. 分页管理列表，接口固定叫 `/pageList`
2. 不分页选项列表，接口固定叫 `/list`

但这不是强制。像 `VIP`、分类这种数据量很小的模块，可以只做 `/list`。

例如分类模块：

1. 如果只是简单配置和选择，直接用 `/list`
2. 如果后续后台筛选和数据量增长明显，再补 `/pageList`

这两种接口不要混写成一个。

## 4. 分页列表和不分页列表的写法区别

### 4.1 分页列表的目标

分页列表用于后台表格管理，接口命名固定为：

```text
方法名：PageList
路径：/pageList
```

特点是：

1. 支持 `page`
2. 支持 `pageSize`
3. 支持筛选条件
4. 返回 `list + total`

推荐返回结构：

```json
{
  "list": [],
  "total": 0,
  "page": 1,
  "pageSize": 10
}
```

适合：

- 管理页表格
- 用户类列表
- 明显会增长的业务数据

### 4.2 不分页列表的目标

不分页列表用于取全部可用选项，接口命名固定为：

```text
方法名：List
路径：/list
```

特点是：

1. 不传 `page`
2. 不传 `pageSize`
3. 通常只保留轻量筛选
4. 直接返回数组或轻量列表结构

推荐数据形态：

```json
[
  {
    "id": 1,
    "name": "普通会员"
  }
]
```

或者：

```json
{
  "list": []
}
```

适合：

- 下拉框
- 单选/多选弹窗
- 级联选择器
- `VIP` 等级管理
- 分类管理

### 4.3 查询条件也不一样

分页列表通常支持：

1. 名称
2. 状态
3. 时间范围
4. 关键词

不分页列表通常只保留：

1. 状态
2. 父级 `id`
3. 简单关键词

原则：

不分页列表要轻，不要把后台复杂筛选整套搬过去。

### 4.4 排序规则也要稳定

配置型模块列表默认建议：

1. 先按 `sort` 升序
2. 再按 `id` 升序或创建时间升序

这样能保证：

1. 运营调整排序后结果稳定
2. 相同排序值时结果不乱跳

## 5. 配置型 CRUD 的默认接口建议

如果是一个标准后台配置模块，默认建议至少有这些接口：

1. `List` 不分页选项列表，路径 `/list`
2. `Detail` 详情
3. `Create` 新增
4. `Update` 修改
5. `Delete` 删除
6. `UpdateStatus` 单独状态切换接口
7. `PageList` 分页列表，路径 `/pageList`，当数据量或后台检索场景明确存在时再补

### 5.1 为什么建议单独做 `UpdateStatus`

因为后台经常只是切换启用/禁用，不想每次都走完整编辑表单。

所以对配置型模块，单独做状态切换接口通常更实用。

适合单独做状态切换的模块：

1. 分类
2. `VIP` 等级
3. 品牌
4. 标签

## 6. 删除、停用、排序的默认处理

### 6.1 什么时候删，什么时候停用

如果数据会被前台引用，优先考虑“停用”而不是“硬删”。

建议：

1. 可被历史订单、用户记录引用的数据，优先停用
2. 纯后台误建、无引用的数据，才考虑删除

所以很多配置型模块虽然有删除接口，但真实使用中更常用的是：

1. `status` 禁用
2. `sort` 调整

### 6.2 排序字段不要省

如果这个模块明显会出现在前台展示、下拉、列表、导航中，就不要偷懒省掉 `sort`。

经验上，后面再补排序字段，成本通常更高。

## 7. 你给 Codex 提需求时，推荐这样说

### 7.1 `VIP` 等级配置 CRUD

```text
按本项目规范，为 VIP 等级配置模块实现后台 CRUD。
这是后台模块，接口走 /admin-api。
字段至少包含：名称、等级值、状态、排序、备注。
默认按小数据配置模块处理，先实现 `/list` 不分页列表。
请求和返回字段写中文注释。
如果适合，补一个单独的状态切换接口。
改完执行 go build ./...。
```

### 7.2 分类配置 CRUD

```text
按本项目规范，为分类配置模块实现后台 CRUD。
这是后台模块，接口走 /admin-api。
字段至少包含：名称、状态、排序、备注。
默认按小数据配置模块处理，先实现 `/list` 不分页列表。
如果你认为后续数据会增长，再补 `/pageList`。
请求和返回字段写中文注释。
改完执行 go build ./...。
```

### 7.3 品牌配置 CRUD

```text
按本项目规范，为品牌配置模块实现后台 CRUD。
这是后台模块，接口走 /admin-api。
字段至少包含：名称、Logo、状态、排序、备注。
品牌数量我不确定，你先按本项目规范判断是否只做 /list，还是同时补 /pageList；如果拿不准就先提醒我确认。
请求和返回字段写中文注释。
改完执行 go build ./...。
```

### 7.4 用户列表 CRUD

```text
按本项目规范，为后台用户模块实现 CRUD。
这是后台模块，接口走 /admin-api。
用户列表默认必须使用 /pageList。
分页列表支持按关键词、状态等条件筛选。
请求和返回字段写中文注释。
改完执行 go build ./...。
```

## 8. Codex 的默认理解

如果你说：

```text
帮我做一个分类配置 CRUD
```

那 Codex 默认应理解为：

1. 这是后台配置型模块
2. 默认走 `/admin-api`
3. 默认考虑 `status`
4. 默认考虑 `sort`
5. 默认先做 `/list`，因为分类通常是小数据配置
6. 只有在你明确说数据会增长，或者后台检索场景明显时，再补 `/pageList`
7. 请求和响应 DTO 写中文注释
8. 最后执行 `go build ./...`

如果你没明确反对，这套默认理解可以直接用。
